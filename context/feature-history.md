Neon in Prisma 7 needs only `@prisma/adapter-neon`, not `@neondatabase/serverless` or `ws`.

  - **Schema** (`prisma/schema.prisma`): Prisma 7 header (`prisma-client` generator, output `../src/generated/prisma`, no URL in the datasource). 4 enums and 8 models copied from overview section 7.
  - **PropertyType enum:** changed before the first migration to match the homepage dropdown: APARTMENT, STUDIO, CONDO, HOUSE, CABIN_OR_COTTAGE, LOFT, ROOM, OTHER (Townhouse and Basement removed). The overview's enum and property-types table were updated to match.
  - **Config** (`prisma.config.ts`): loads `dotenv/config`, sets the migrations path, and uses `env("DIRECT_URL")`, Neon's direct (non-pooled) connection, for the CLI. Written by hand instead of with `prisma init`, so `.env` wasn't touched.
  - **Migration:** `prisma/migrations/20261001191609_initial_schema/`, applied to the development branch. `prisma migrate status` reports up to date. The production branch was confirmed to have no tables. Prisma 7's `migrate dev` doesn't run `generate`, so `npx prisma generate` was run separately.
  - **Client** (`src/lib/db.ts`): `PrismaNeon` adapter using the pooled `DATABASE_URL`, with a `globalThis` singleton outside production. Server-only.
  - **Housekeeping:** `/src/generated/prisma` and `!.env.example` added to `.gitignore`. `"postinstall": "prisma generate"` added to `package.json`. Because `prisma generate` loads `prisma.config.ts`, `DIRECT_URL` must be set wherever `npm install` runs, including on deploy. `.env.example` lists `DATABASE_URL` and `DIRECT_URL` with no values.

Still to do at deploy time: keep production credentials off local machines, run `migrate deploy` only in the deploy pipeline, and give the app a Postgres role with data-only privileges.

- **Auth Phase 1:** NextAuth v5 with Google OAuth, JWT sessions, and role-based dashboards (spec: `context/features/auth-phase-1-spec.md`). The Database Setup feature already covered the spec's database section, so no schema or migration changes were needed.
  - **Packages:** `next-auth@beta` and `@auth/prisma-adapter`, plus dev dep `vitest`. `npm audit` reports 4 high-severity findings, which weren't investigated.
  - **Split config:** `src/auth.config.ts` is edge-safe, with no Prisma imports. It holds the Google provider, the `jwt`/`session` callbacks that put `id` and `role` on the token and session, the `authorized` callback, and `theme: { colorScheme: "light" }` so NextAuth's default pages don't follow the OS dark mode. `src/auth.ts` adds `PrismaAdapter(db)` and `session: { strategy: "jwt" }`. With the adapter, the `user` passed to `jwt` on sign-in is the DB row, so Google sign-ups get `RENTER` from the schema default with no custom `profile()`.
  - **Types** (`src/types/next-auth.d.ts`): adds `id` and `role` to `Session.user`, and `role` to `User`. The `JWT` augmentation targets `@auth/core/jwt`, because `next-auth/jwt` only re-exports it with `export *` and augmenting the re-export doesn't merge.
  - **Route rules** (`src/lib/routes.ts`): `ROLE_DASHBOARDS`, `getRequiredRole()`, `isProtectedRoute()`, and `resolveRouteAccess()` returning `allow` / `sign-in` / `wrong-role`. Prefix matching is segment-aware, so `/administrator` doesn't count as `/admin`. Shared by the proxy, the `/dashboard` redirect, and tests.
  - **Proxy** (`src/proxy.ts`): `export const proxy = auth` from `NextAuth(authConfig)`, with a matcher limited to the protected paths. `authorized` returns `false` for signed-out users (NextAuth redirects to `/api/auth/signin` with a callback URL) and `Response.redirect('/dashboard')` for the wrong role.
  - **Server guards** (`src/lib/auth-guard.ts`): `getCurrentUser()`, `requireUser()`, and `requireRole(...roles)`. Signed-out users go to `/api/auth/signin` without a callback URL; the proxy normally catches them first. The wrong role goes to `/dashboard`.
  - **Pages:** `/dashboard` redirects with `ROLE_DASHBOARDS[user.role]`. `/renter/dashboard`, `/owner/dashboard`, and `/admin` each call `requireRole()` for their own role only and render `src/components/dashboard/DashboardPlaceholder.tsx` (heading, name, email, role). The only API route is `src/app/api/auth/[...nextauth]/route.ts`, which NextAuth needs for the Google OAuth callback, the default sign-in page, and its CSRF/session endpoints.
  - **Navbar:** now an async Server Component that reads `auth()` and shows Sign In (`signIn()` Server Action, `redirectTo: "/dashboard"`) or Sign Out (`signOut()`, `redirectTo: "/"`). This minimal toggle was pulled forward from phase 3 so roles could be tested; the phase 3 avatar menu replaces it. Reading the session makes every page, including `/`, dynamically rendered.
  - **Buttons:** Tailwind v4 resets buttons to `cursor: default`, so a base-layer rule in `globals.css` gives every enabled `button` and `[role="button"]` the pointer cursor. Documented in `coding-standards.md`.
  - **Testing setup:** `vitest.config.ts` (`@` alias, `src/**/*.test.ts`, `mockReset`, `unstubEnvs`), plus `npm test` and `npm run test:watch`. Vite warns about ESM syntax in a `.ts` config without `"type": "module"`. Harmless; the file name follows the coding standards.
  - **Tests:** 21 unit tests in `src/lib/routes.test.ts`, `src/lib/auth-guard.test.ts` (with `@/auth` and `next/navigation` mocked), and `src/auth.config.test.ts` (the `jwt`, `session`, and `authorized` callbacks).
  - **Setup notes:** `AUTH_SECRET` must be set (`npx auth secret`), or NextAuth returns a 500 `MissingSecret`. Google Cloud Console needs the redirect URI `http://localhost:3000/api/auth/callback/google`. Changing the auth config sometimes needs a dev-server restart before the auth route picks it up.
  - **Testing roles:** there's no role UI. Change `User.role` on the Neon development branch (Prisma Studio or SQL), then sign out and back in, because the role is stored in the JWT at sign-in.
  - **Also in this commit:** the auth phase 2 and 3 specs, `.env.example` variable names, and updates to `.claude/agents/auth-auditor.md` and `refactor-scanner.md`.
  - **Validation:** 21/21 tests, `tsc --noEmit`, lint, and `next build` pass. Google sign-in was confirmed manually by the user as RENTER.
- **Unify USER Role:** Replaced the `RENTER`/`OWNER` roles with one `USER` role and a single `/dashboard` (no spec file; loaded from an inline description after a design discussion). Renter and owner are now activities, not roles: the same account can rent and list, like Airbnb, with no "become an owner" step and no role choice at registration.

Owner routes moved to `/dashboard/properties[/new|/[id]/edit]` and `/dashboard/inquiries`; `/favorites` and `/inquiries` stayed. Users can't send inquiries about their own property. Admin stats are total users and users with listings. The sidebar, auth rules, mutation steps, and checklist were updated to match.

Seeding Olivia's listings waits for the property features. `auth-phase-3-spec.md` has no account-type picker, everyone lands on `/dashboard`, and the navbar menu shows Dashboard plus Admin for admins only.
  - **Migration** (`prisma/migrations/20261001220000_unify_user_role/migration.sql`): hand-written, because `prisma migrate dev` refused to run non-interactively over the enum-value warning, and Prisma's own SQL would fail on existing `RENTER` rows. It creates `Role_new` (`USER`, `ADMIN`), casts with `CASE WHEN role = 'ADMIN' THEN 'ADMIN' ELSE 'USER'`, swaps and drops the old type, and sets the default to `USER`, inside `BEGIN`/`COMMIT`. No rows are deleted. Applied to the development branch with `prisma migrate deploy`; `prisma migrate diff --from-config-datasource --to-schema` reported no difference, and `migrate status` is up to date.

The proxy matcher is now `/dashboard/:path*` and `/admin/:path*` plus the signed-in routes. `Inquiry.renterId` kept its name (documented as "the user who sent the inquiry") to avoid a second schema change.
